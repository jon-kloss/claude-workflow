# Adaptive Developer Workflow — Full Evaluation

*Assessment date: 2026-07-04. Branch: `experiment/role-agents` with uncommitted changes (audited as on disk). All findings verified against file content or live command output; two harness-behavior items are explicitly marked as needing a live check.*

## Verdict

The design of this system is genuinely good: the spec lifecycle is coherent, the finder-verifies/implementer-fixes loop is the right shape, the override-with-audited-reason mechanism is better than anything I've seen in comparable setups, and the newest layer (Mount Map / integration spec) attacks a real, documented failure. But the implementation has drifted badly out of sync with itself across three generations of refactors (inline → orchestrator prose → role agents), and **several of the load-bearing gates are provably inert or self-defeating as shipped**. The system currently earns its trust from the prose discipline of the skills, not from the hooks — the deterministic enforcement layer is roughly half theater right now. Separately, about a quarter of the ~7,600 lines of prompt text is Sonnet-3-era defensive scaffolding that now dilutes the real constraints.

**The five highest-payoff changes:**

1. **Empirically settle how hooks and interactive tools behave inside subagents, then re-architect around the answer.** Current Claude Code docs state that (a) `AskUserQuestion` is unavailable inside subagents, and (b) settings.json PreToolUse/PostToolUse hooks do not fire for tool calls made inside subagents (only SubagentStart/Stop). If (a) holds, the flagship Socratic step is broken as designed — `/design` Step 2 dispatches product-owner as a subagent and tells it to "Use AskUserQuestion to probe requirements" (`skills/design/SKILL.md:144-152`), which cannot surface to you. If (b) holds, every Edit/Write gate binds only the orchestrator, and any role agent that writes a spec status (as `/respec` Step 4 explicitly instructs engineers to do) bypasses the whole gate layer. If (b) does *not* hold in your installed version, you instead have the guard-handoff-owner deadlock (finding H1 below). Every branch of this is critical; a 15-minute experiment (dispatch a trivial agent that calls AskUserQuestion and writes `@status(verified)` into a scratch spec) resolves which failures you actually have.
2. **Fix the verification state machine — it is inert against its own dispatch templates.** The continuous-verifier pipeline extracts IDs the build skill's template never produces, so `block-status-during-verification.sh` can never match anything real (findings H2–H4), and all session state lives in one global, unkeyed directory that is truncated on compaction and shared across concurrent sessions (H5).
3. **Make the install ship what the system needs.** `hooks/require-feature-mounted.sh` is registered in settings but untracked in git (fresh clones get a failing hook on every edit); `resources/` directories are never linked, so the Gherkin reference, all 17 memory templates, and the game-context template are unreachable on any installed machine; uninstall reverses a fraction of install (I1–I4).
4. **Adopt one canonical vocabulary for step IDs and handoff filenames, and generate everything else from it.** There are currently four step-numbering schemes (3.3c.1 vs 3.3.1 vs 3.3.2/3.3.3 vs unnumbered), two fix-cycle filename conventions, phantom steps (3.3e/3.3f) referenced five times, and a schema doc that contradicts its own rules twice. Roughly a third of all machine-level findings below are downstream of this one problem (M1–M14).
5. **De-scaffold the prompt corpus (~25% token reduction, better compliance).** Extract the identical 30-line exit-checklist block pasted into all 16 agents, cut the ~90 "common rationalizations" bullets in build/design alone plus ~90 more across agents, delete the Playwright tutorial from qa-engineer, and promote the handful of genuinely policy-bearing bullets into normative sections (P1–P9). Also close the retrospective loop, which currently never fires from where it's documented to fire (R1–R3).

## Theme A — Foundational: subagent capabilities vs. the design's assumptions

**A1. Critical — Socratic-via-subagent cannot work as written.** The docs for Claude Code subagents list `AskUserQuestion` among tools that "depend on the main conversation's UI … and aren't available to subagents, even when listed in the tools field." Yet the design leans on exactly that: product-owner Step 2 ("Use AskUserQuestion to probe requirements", `skills/design/SKILL.md:148`), the Step 4 reality check ("Present specs to user via AskUserQuestion" from inside the PO dispatch, `design/SKILL.md:351`), `product-owner.md:22` ("Use the AskUserQuestion tool. Never present questions as plain text"), all five game agents ("STOP and AskUserQuestion"), and build's Step 3.3h cycle-cap escalation. No prompt has a fallback. In practice the questions either vanish or degrade into non-blocking text inside a subagent transcript you never see. Fix direction: either the orchestrator asks (agents return question lists in `open-questions` and the parent relays them via AskUserQuestion), or those steps run inline. Add the fallback line to every agent that assumes interactivity.

**A2. Critical — the hook layer's reach over role agents is unverified and version-sensitive.** Per the same docs, project settings.json hooks fire only on subagent start/stop, not on tool calls inside subagents. The workflow's whole premise — "hooks deterministically block skip patterns" — assumes the opposite whenever the writer is a subagent: engineers set `@status(implemented)` during Step 3.2 (`build/SKILL.md:393`), respec dispatches engineers to "regress @status to @status(approved)" (`respec/SKILL.md:195`), and role agents write their own handoffs. Note the internal tension: the hooks audit's deadlock finding (H1) assumes hooks *do* fire in subagents. Both cannot be true; whichever holds, something critical is broken. If gates don't bind subagents, the fix is per-agent frontmatter hooks (documented as supported) or routing all status writes through the orchestrator.

**A3. Important — the inline-synthesis fallback quietly halves the system's value and no artifact records which mode ran beyond one note.** `design/SKILL.md:18` and `build/SKILL.md:19` allow a dispatched subagent to impersonate every role inline, marking only `<note data-synthesized="true">`. Nothing downstream (release-coordinator, retro, hooks) reads that marker, so a fully-synthesized epic is indistinguishable from a genuinely multi-perspective one at close time.

## Theme B — Gate logic: hooks that don't do what they claim

All verified at the cited lines.

**H1. Critical — `guard-handoff-owner.sh` deadlocks the first dispatch of every role (if hooks fire in subagents).** It blocks handoff writes unless the role appears in `session-agents.log` (`guard-handoff-owner.sh:117-127`), but that log is written by `track-agents.sh`, registered as a **PostToolUse** Agent hook (`install.sh:373-375`) — it records a dispatch only when the agent *returns*. The agent writes its handoff *during* the run. So the first dispatch of any role is blocked from writing the artifact its exit checklist demands, which plausibly *manufactured* the "implementer did the work but returned without its handoff, observed twice" incident that 16 agent files now carry boilerplate to prevent. Fix: log dispatches at PreToolUse.

**H2. Critical — the continuous-verifier pipeline is inert against its own template.** `verifier-dispatch.sh:54-55` extracts `Task:\s*(bd-\d+)` and `Epic:\s*(bd-\d+)`; the documented dispatch prompt (`build/SKILL.md:361-380`) contains `Task: [current task description]`, no `Epic:` line at all, and pasted spec *contents* rather than a path. Every inflight record is `unknown|unknown|`, so `block-status-during-verification.sh:72,101` can never match, and `verifier-return.sh` never logs its bd comment. The "never update status while verification is in flight" rule is enforced by prose only. Also `bd-\d+` doesn't match your actual bead ID shape (`workflow-xxx`).

**H3. Important — `block-status-during-verification.sh:96` truncates IDs to exactly three characters** (`[a-z]+-[a-z0-9]{3}` without `{3,}`), so `bd close workflow-4f2a` extracts `workflow-4f2` and never matches; the bd-close arm is bypassed for any realistic ID. Compare `require-release-handoff.sh:46`, which gets it right.

**H4. Important — the epic-close gate's BLOCKED branch has no working override, and the override command is spelled three ways.** `require-release-handoff.sh` checks `RELEASE-SKIP:` comments only in the missing-handoff branch (:86-91); the BLOCKED-verdict branch (:119-129) prints the override instruction and then exits 2 unconditionally — following the hook's own advice does nothing; the only escape is editing the handoff verdict, exactly the tampering the system exists to prevent. The hook says `bd comment`, the skills and README say `bd comments add` (`build/SKILL.md:788`, `README.md:406`), and release-coordinator.md:63 invents a third form, an `@release-skip(reason)` spec tag no code reads.

**H5. Critical — global, shared, compaction-wiped session state.** All evidence (`session-reads.txt`, `session-agents.log`, `session-skills.log`, `verifier-inflight.txt`) lives unkeyed in `~/.claude/hooks/state/`, and `clear-session-reads.sh` truncates it on SessionStart matcher `startup|clear|compact` (`install.sh:231`). An auto-compaction mid-epic erases the record that verifier agents ran, so the next `@status(verified)` write is falsely blocked — training you (and the model) to reach for override tags, which corrodes the audit trail's meaning. Two concurrent sessions in different projects clobber each other the same way. State should be keyed by session/project.

**H6. Important — `require-ui-tests.sh` framework detection is broken under `set -o pipefail`.** `ls "$root"/playwright.config.{ts,js,mjs,cjs} | head -1` (:112, :116, :123) fails unless *all four* extensions exist, so config-file detection never succeeds; Playwright/Cypress survive only via the package.json fallback and vitest-browser detection is dead. Monorepos with root-level deps get a false "no UI test framework installed" block.

**H7. Important — `require-feature-mounted.sh` (the newest gate) has three correctness holes:** (1) `@integration\b` matches `@integration-skip`, so a feature spec carrying the *skip* tag is misclassified as the integration spec (:100, :143); (2) Mount-Map membership is a plain substring grep — slug `chat` passes if the map contains `chat-window`, and the code-import rescue (:201-213) accepts the slug appearing in a comment anywhere in the source tree; (3) the ≥2-UI-spec threshold counts all of `specs/`, so verified specs from a previous epic push a single-feature epic over the threshold, contradicting its own header comment (:19-21).

**H8. Important — probable harness-schema drift silencing hooks (needs a live check, listed as suspected).** `detect-correction.sh:19` and `workflow-reminder.sh:18` read the prompt from `.text`; the documented UserPromptSubmit field is `prompt`, with no fallback present — if the docs match your version, correction detection (the retro's incident feed) never fires. Similarly, every advisory hook emits top-level `{"additionalContext": ...}` via `_common.sh:58-64` where the documented shape is `hookSpecificOutput.additionalContext`; and `wwiwo.sh` depends entirely on a `"matcher": "wwiwo"` on a UserPromptSubmit hook (`install.sh:420`) — matchers are documented for tool events, and the script itself never inspects the prompt, so it either never runs or runs on *every* prompt. PostToolUse extraction in `molecule-autoclose-warn.sh:50-56` and `verifier-return.sh:44-49` omits the documented `tool_response` field. One session with `claude --debug` would confirm all four.

**H9–H16. Minor gate defects, briefly:**
- `require-release-handoff.sh:46` grabs the first ID-shaped token in the command (`cd my-project && bd close epic-123` inspects `my-project`), and multi-ID closes gate only the first ID.
- Verdict extraction (:105-111) returns whichever of BLOCKED/READY-* appears first anywhere in the HTML prose, not the verdict line.
- `require-fix-cycle-handoff.sh:94` — slug `foo` matches spec `foo-bar`'s cycle files, inheriting phantom asymmetry.
- `block-unread-edits.sh:54,61` substring matching: a read of `b.tsx` satisfies `b.ts`; one read anywhere in a directory unlocks the whole directory; and with a missing reads file it blocks even new-file creation (:15-20 precedes the new-file allowance).
- `guard-spec-bash-writes.sh` is bypassed by variable indirection (`f=specs/foo.md; echo ... > $f`), `cd specs && cat > foo.md`, and `git checkout -- specs/foo.md`.
- `check-open-beads.sh:12-13` — `grep -c ... || echo 0` yields `"0\n0"`, throwing "integer expression expected" on every Stop event in a clean project.
- `require-bead-description.sh` and block-status's Bash arm fire on *mentions* (`echo "then run bd create"`), not invocations.
- `require-investigation-findings.sh:82-98` checks only "≥3 non-blank lines" while the skill promises ≥2 file:line refs and a `Decision:` line (`build/SKILL.md:302`) — three lines of filler pass.
- Hardcoded `python3` in five gate hooks (`claim-vs-call-audit.sh:102`, `guard-handoff-owner.sh:99`, `require-fix-cycle-handoff.sh:113`, `require-handoff-artifact.sh:198`, `warn-agent-memory-not-updated.sh:101`) bypasses `_common.sh`'s own Windows Python-stub workaround, turning every legitimate override into a garbage-error block on such machines; and if Python is absent at runtime, every gate silently allows everything (`_common.sh:14` → `echo '{}'`).
- Hot-path cost: `require-feature-mounted.sh` greps the whole source tree on UI-spec status writes; `check-open-beads.sh` runs two `bd list` calls plus a recursive grep after every turn.

## Theme C — Machine drift: skills, agents, schema, and hooks disagree

**M1. Critical — `require-design-ui.sh` speaks a tag vocabulary the system abandoned.** Its escape hatch (:80) is `@backend-only|@api-only|@cli|@infra` and it never checks `@layer(...)`. A spec correctly tagged `@layer(api)` that mentions "input", "view", "list view", or "component" (the UI_PATTERNS list at :87 is very broad) is blocked at approval and told to add `@backend-only` — a tag taught by no skill; `@api-only` appears nowhere else in the repo; and the literal `@cli` pattern does not match `@layer(cli)`.

**M2. Critical — spec-sre-auditor is self-contradictory: its exit checklist orders it to "write your handoff file to the path documented in 'What you produce' above" (`spec-sre-auditor.md:108`), and no such section exists in the file.** It defines only a plaintext verdict format, yet `require-handoff-artifact.sh` and release-coordinator both depend on a handoff artifact it is never told how to produce.

**M3. Critical — step numbering has four coexisting schemes.** Build uses 3.3c.1/3.3c.2/3.3c.3 (`build/SKILL.md:467,484,498`); devops-architect's frontmatter says "Step 3.3.2" and its body invents "Step 3.3.1"; data-architect and `gherkin-spec-reference.md:23` and `design/SKILL.md:82` say "Step 3.3.3"; security-architect's frontmatter uses no number. The schema doc says the handoff filename step-id "is the dotted step number from the SKILL.md" (`role-agent-handoff-schema.md:21`) — which is not decidable when the SKILL.md itself has three names for one step.

**M4. Critical — build references steps that no longer exist.** "Step 3.3f (API Integration Check)" is cited at `build/SKILL.md:403, 975, 1014, 1081` and "Step 3.3e" at :977, but both were consolidated into 3.3d (the file says so at :514). An agent told "Step 3.3f is mandatory" (rule 20) will search for a section that isn't there. Likewise the integration table (:1116-1123) still maps nine impeccable gates to "Step 3.3d D2…D9" dimension labels from the pre-consolidation version — while rule 18 (:973) *also* still orders the orchestrator to run critique/detect/polish itself, duplicating what 3.3d now delegates to qa-engineer.

**M5. Critical — /build contradicts itself on whether verification scales down.** ":417 'Full verification. NEVER scales down. Identical for every spec.'" and the rigidity block and the typo example (:828) — versus "Skip when: Spec is `@trivial`" on security review (:483), devops review (:496), and QA verification (:538). Both cannot be the rule; as written, a `@trivial` tag turns off the three deepest reviewers while the skill loudly claims nothing ever does.

**M6. Important — qa-engineer's own prompt breaks the pipeline's ordering.** `qa-engineer.md:15` says it arrives "AFTER the architectural reviewers (security, devops, data, code-reviewer, **sre-auditor**)" and :29 "after the per-spec reviewers (3.3a–3.3g)" — but QA *is* 3.3d, which build places before 3.3g. And frontend-engineer's frontmatter still claims "Step 3.3d (visual fidelity)" while qa-engineer's frontmatter claims 3.3d as "authoritative" — two owners for one step label.

**M7. Important — fix-cycle filename convention is split.** Build and the hook require reviewer re-verifies at `step-3.3-<slug>-<role>-cycle-N.html` (`build/SKILL.md:645,672`; `require-fix-cycle-handoff.sh:11`), while the schema doc's canonical example uses `...-devops-architect-fix-cycle-1.html` (`role-agent-handoff-schema.md:130`), and game-ui-designer writes fix handoffs at `step-2.85-...` (:82), which the hook (implementer side pinned to `step-3.2`) can never see — an agent following its own prompt gets blocked for "asymmetry." The hook's loose `.+-cycle-N` regex happens to accept both reviewer spellings, which also means an implementer-named file at step-3.3 satisfies the reviewer requirement.

**M8. Important — the schema doc contradicts itself twice.** (1) Hook check #3 requires the five meta attributes "present and non-empty" (:334) while the attribute table says `data-input-references` is "Empty if no prior handoffs" (:52) and Example 1 ships it empty (:222). (2) Line 175 says advisory agents "always route to an implementer (backend-engineer, frontend-engineer, or uiux-designer)" while the canonical table three lines up includes application-architect, devops-architect, and product-owner — and qa/data/devops route to all three "illegal" targets in their prompts.

**M9. Important — verdict vocabulary is fragmented and mostly machine-invisible.** spec-sre-auditor: `PASS | FAIL (critical) | FAIL (spec-drift)`; release-coordinator: `READY-TO-CLOSE | READY-WITH-CAVEATS | BLOCKED` with no anchor element; qa-engineer, security-, devops-, data-architect define no verdict line at all — yet release-coordinator's frontmatter promises to verify "every verifier verdict is PASS," which is mechanically impossible against four of five verifiers. SPEC-DRIFT has no legal `data-severity` encoding (schema allows `critical|important|suggestion`). One `<meta data-verdict>` in the required head would fix the class.

**M10. Important — the data-architect gate is unconditional in the hook, conditional in the skill.** `require-handoff-artifact.sh:180-184` demands a data-architect handoff for every `@layer(api|full-stack)` spec; `build/SKILL.md:510` triggers it only for `@touches-data` or DB operations in Technical Context (and build's own table at :281-283 sides with the hook). A DB-free proxy endpoint pays a 30-character validated override.

**M11. Important — /build Phase 2 confirms a parallelism that nothing implements.** The dependency-graph step computes parallel lanes and asks you to "Confirm parallel execution?" (`build/SKILL.md:225-255`), then Phase 3 iterates strictly sequentially (:271, :724-730); there is no worktree or concurrent-implementation mechanism anywhere. The confirmation is theater, and `--auto` (":39 Autonomous — runs end-to-end") still blocks on this AskUserQuestion because only Step 3.4 checks the flag (:166-168).

**M12. Important — /design's entry rules conflict with its role split.** Rule 10 (:607) and a rationalization (:634) say "/design-ui runs BEFORE spec generation … invoke `/design-ui`" while Step 2.85 dispatches the uiux-designer *agent* instead; and design-ui's own Phase 3 gates grep `specs/<slug>.md` and require an epic-id bd comment (`design-ui/SKILL.md:321,362`) — neither specs nor epic exist yet at Step 2.85 (beads setup is Step 5). Coherent standalone, incoherent on the primary path. Also: the critical-rules list numbering jumps 11 → 14 (`design/SKILL.md:608-609`), and "No codebase investigation during design" (rule 2) sits awkwardly against a decomposition step whose whole job is finding seams in an existing codebase — /onboard memory partially covers this, but the tension is never addressed.

**M13. Important — /respec's handoffs break the schema.** Blast-radius goes to `step-3-<slug>-application-architect.html` (`respec/SKILL.md:149`) — sharing the `step-3` prefix namespace with build — and propagation handoffs go to `respec-<downstream>-<role>.html` (:196), which violates the schema's `<step-id>-<spec-slug>-<role>` location rule outright; whether `require-handoff-artifact.sh` tolerates them is undefined. Also, /respec has engineers (implementer agents) editing spec files, while rule 8 says "respec edits specs, /build implements" — a role blur that guard-spec-bash-writes/guard-handoff-owner weren't designed around.

**M14. Minor machine drift, briefly:**
- build's integration table says the skill "consumes … Beads epic with per-spec tasks" (:1135) while :203 says per-spec tasks are created *by* /build; and Step 3.1 never actually contains the "create implementation task" instruction the checklist (:1048) assumes.
- The system agent registry says product-owner runs "/build Step 3.4 (user sign-off)"; build's Step 3.4 is inline AskUserQuestion and never dispatches it.
- `data-step` meta format (`design.2.5-decomposition`, schema :36) is specified nowhere agents would learn it; every dispatch improvises.
- The schema promises hooks cross-reference `data-produced-at` against `session-agents.log` (:48) and require `data-route-to` on critical/important asides (:177) — `_validate_handoff.py` does neither.
- uiux-designer produces N handoffs per invocation (`uiux-designer.md:39`) against the schema's "exactly one" (:7); it is also a routing target for fixes but has no fix-mode section, while `game-ui-designer.md:74` inherits "the same protocol as uiux-designer's fix mode" — which doesn't exist — and names a different "same" gate pipeline (teach/craft/critique/detect/enhance vs critique/audit/harden/clarify/adapt).
- game-ui-designer's activation condition (frontmatter: `@surface(game)` *or* game-context exists) is broader than design's per-spec `@surface(game)` routing (:269-277) — a game project's plain settings page loses uiux-designer entirely.
- Stale line-number citations inside four hooks' headers and block messages (e.g. `block-status-during-verification.sh:7` cites "SKILL.md:1216" in a 1181-line file).
- README's layer list omits `gameplay`, which `require-layer-tag.sh:67` accepts.
- level/narrative designers each "read the other if available" while dispatched in parallel — race-dependent inputs.
- design :16 tells you to verify parallelism by checking that `data-produced-at` timestamps "overlap" — second-granularity timestamps of variable-length runs are an unreliable check.
- `/design-ui` requires a `detect` gate five times (:42, :55, :337, :401, :427) that the impeccable plugin does not expose as a command (anti-pattern detection lives inside `critique`) — and its own rigid gate list (:16) doesn't include it. Gate-count arithmetic disagrees with itself (20 vs 12 vs 24 calls at :17, ~415, :491).

## Theme D — Install, uninstall, distribution

**I1. Critical — a fresh clone is broken: `require-feature-mounted.sh` is registered in settings (`install.sh:275`) but untracked in git.** Anyone (including you on a second machine) installing from a clean clone gets a settings entry invoking a nonexistent file — a failing hook command on every Edit/Write. Commit it. Same discipline problem: `specs/incident-logging.md` and `specs/retrospective-overhaul.md` are `@status(verified)` yet untracked — verified specs that were never committed.

**I2. Critical — installed skills lose their `resources/`.** install.sh links only `SKILL.md` files (`install.sh:139-146`); verified: `~/.claude/skills/design/` and `~/.claude/skills/onboard/` contain nothing else. Consequences: the Gherkin spec reference that /design links four times is absent at its installed-relative path; all 17 memory templates that every agent's bootstrap instruction points at are unreachable; the game-context template too. Compounding it, every agent's bootstrap path is *repo-relative* ("bootstrap from `skills/onboard/resources/memory-template-<role>.md`", `application-architect.md:81`) and resolves to nothing from a project cwd even if the files were linked.

**I3. Important — uninstall.sh reverses a fraction of install.** It removes 6 of 7 skills (onboard orphaned), 1 of 16 agents (`uninstall.sh:80` — only spec-sre-auditor; 15 role agents stay dispatchable "after uninstall"), and 12 of 35 hooks (:87-92 — every require-*/guard-* gate and all Python validators remain). Two settings entries (track-skills, molecule-autoclose-warn) contain no legacy script name and survive removal — after deleting the repo they become dangling symlinks erroring on every Skill and Bash call. Worse, uninstall deletes an entire merged settings entry if *any one* command in it matches its legacy list (:133-144), destroying a user's own pre-existing same-matcher hooks. The README's uninstall claims ("removes all… restores settings.json from backup", `README.md:524-535`) are both false as shipped. Rewrite uninstall from a manifest generated by install.

**I4. Important — dependency and environment gaps.** install checks only python3 (:34-49); nine hooks shell out to `bd`, and `require-release-handoff.sh:53-56` exits 0 when bd is absent — the epic-close gate silently vanishes. `is_our_file` treats any symlink as "ours" (:93-95), so dotfiles-managed skills get deleted without backup. `read -p` at :496 under `set -euo pipefail` kills non-interactive installs after hooks are linked but before the summary. The superpowers-disable step is never reversed. Minor: summary omits onboard and prints `$(pwd)/benchmarks` (wrong unless run from repo root); the settings merge dies with a raw traceback on non-strict-JSON settings, half-installed.

**I5. Minor — repo hygiene.** `.gitignore` covers only `.dolt/` and `*.db`: `hooks/__pycache__/` should be ignored; `package-lock.json` (170 KB, `"name": "brewery-api"`, no package.json anywhere) is residue to delete; `vendor/hyperpowers` is unexplained and contradicts README:237's plugin story — the role-agent system hard-depends on `hyperpowers:*` agents (`backend-engineer.md:112`) with no documented fallback if the plugin is missing.

## Theme E — Prompt fitness for a frontier model

**P1. Important — ~500 lines of identical boilerplate pasted into all 16 agents.** The exit-checklist/TERMINAL block, the fix-cycle hook paragraph, the SquashBuckler anecdote (told 19 times across 16 files; release-coordinator tells itself the story three times), and the sleep-polling note (which itself admits "the Bash tool description explicitly forbids this pattern") appear verbatim ×16 — including in seven roles that have no fix mode the text refers to. This is ~20% of the corpus. Extract to one shared reference (the schema doc is the natural home) and keep one line per agent: the exact handoff path.

**P2. Important — the rationalization lists have outgrown their purpose.** /build carries ~46 strawman bullets (:984-1031), /design ~37 (:615-651), agents ~90 more, design-arch ten, design-ui fifteen plus a "self-honesty check" interrogating the model about sentences it might write (`design-ui/SKILL.md:524-531`). These were armor for weaker models; on a frontier model they dilute the few policy-bearing bullets (pixel-diff opt-in, carry-forward severity rule, mount-at-decomposition) that should be promoted into normative rules. The same applies to design-arch's HTML skeleton tutorial (:161-183), qa-engineer's Playwright API tutorial (:86-104 — actively misleading when the detected framework is Cypress/Detox), the 8-branch framework-detection tree a sentence would cover, and workflow-retrospective's spelled-out percentage arithmetic (:108-132).

**P3. Important — every skill mandates announce lines ("I'm using the /X skill to…") that your own global CLAUDE.md bans as compliance narration.** The installed system instructs the exact behavior your output rules prohibit, every session.

**P4. Important — missing leverage: context economy.** The schema explicitly provides for reading only `summary` + `acceptance-criteria` sections (:351), yet no prompt uses it — release-coordinator reads "every spec in full, every handoff file" (`release-coordinator.md:28-29`), qa-engineer reads all prior reviewer handoffs in full. On a 10-spec epic this is tens of thousands of wasted tokens per dispatch.

**P5. Important — missing leverage: parallelism below the orchestrator.** The parallel-dispatch pattern exists only at orchestrator level. design-arch dispatches application-architect then devops-architect sequentially (:100-123) even though /design:16 names exactly that pair as the canonical parallel example; design-ui mandates serial execution of 20+ independent gate invocations (the biggest wall-clock cost in the whole pipeline for a multi-spec app); qa-engineer's per-journey e2e authoring and the retro's per-epic bd sweep are embarrassingly parallel and prescribed serial.

**P6. ## What the workflow does well — do not break these

- **The lifecycle spine is right.** draft → approved → implemented → verified with regression via /respec, dependency-ordered build, and blast-radius propagation is a genuinely sound state machine; /respec in particular is the best-written skill in the set (clear classification table, deterministic propagation checks at :202-207, full-content acceptance gate).
- **The override philosophy is exceptional.** Validated override reasons (length + concrete-reference + stop-phrase blocklist in `_validate_override_reason.py`), persisted audit log, and "bypass persists as audit trail" is a better answer to gate fatigue than anything I know of. The resolution chain for critical asides (`data-resolved-in`/`data-re-verified-in` making the one-character bypass require forging artifacts, schema :122-158) is excellent design — keep it, and make the retro actually read the ledger.
- **The Mount Map / integration-spec rollout is the right fix for a real failure**, applied at the right point (decomposition, not rescue), with defense in depth (decomposition rule → per-spec hook → epic e2e reachability → release-coordinator orphan check). Its problems are implementation bugs (H7), not concept.
- **HTML handoffs with four required machine-parsable sections** are a good artifact format: auditable in a browser, greppable by hooks, summary-section context economy already designed in (just unused).
- **The finder-verifies/implementer-fixes routing** (`data-route-to`, fix cycles, cycle cap with escalation) is the correct shape for multi-agent verification; build's Step 3.3h is rightly called the most important orchestration step.
- **Incident-grounded rules.** The best bullets in the corpus cite a dated incident, the enforcing hook, and the override syntax (devops-architect's carry-forward rule is the model). The failure-anchored `<why_it_fails>` example style in the skills is genuinely instructive — it just needs pruning, not removal.
- **The identity paragraphs opening each agent prompt** ("You are the X. Your domain is…") are crisp and worth keeping verbatim.
- **/onboard's design** (lazy/eager split, per-role memory files, refresh deltas) is the right memory architecture; it's the distribution (I2) and small internal contradictions that let it down.
- **The dogfooding instinct** — specs for the workflow's own changes, a smoke test with real hook payloads, benchmarks with an A/B protocol — is rare discipline. The practice is a strength even where the artifacts have rotted.

## Closing observation

Almost every critical finding here is invisible to prose review and would have been caught by an end-to-end integration test — one scripted run of /design → /build on a two-spec toy project, asserting that each gate actually blocks when it should and passes when it should. The smoke test validates hooks in isolation with hand-built payloads; nothing ever validates the *composition*, which is exactly where the system is weakest. If you build only one new thing from this report, build that harness — it converts most of this document from "audit findings" into "failing tests."
